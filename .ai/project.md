# Настройки конкретного контеста

Этот файл — редактируемый источник правил проекта. Заполните неизвестные поля
по репозиторию и официальным условиям игры. Значение «не задано» не является
командой и не разрешает агенту выдумывать её. После изменений выполните синхронизацию.

Параметры проверяются через `Params.apply` и на допустимость в строковом литерале, печатаются действующие; лимит 100 000 символов. Больше одного аргумента — ошибка (на Windows кавычка в `-Pparams` разрывает аргумент). Все проверки, включая имена файлов и единственность маркера PARAMS, идут до записи. Новый артефакт собирается в `build/submit.new` и заменяет `build/submit` только после компиляции, так что любой сбой оставляет старый артефакт целиком; сбой виден по коду выхода 1 (procCheck тогда не запускается). В артефакт записывается build id: первые 8 hex sha256 его текста с пустым литералом BUILD (`cr.submit.Build`); `submit` печатает его рядом с sha256, маркер BUILD обязан встретиться ровно один раз, второго литерала BUILD быть не должно (проверка до записи). Печатается и config id — первые 8 hex sha256 кода от `class Player {` до секции раннера (без заголовка импортов, куда попадают и импорты раннера) плюс значение PARAMS как написано (`Build.config`): сборки, различающиеся только раннером (например, меткой), имеют общий config id; по-разному записанные параметры (`""` и умолчания явно) — разные. Артефакт печатает build id на ходу 0 (строка «Метка сборки в реплее») |
| Проверка точного артефакта отдельным процессом | Перед каждой вставкой: `./gradlew procCheck -Popp=v01 -Pgames=100 -PseedBase=5000` и `-Popp=boss -Pgames=100 -PseedBase=6000` (зависит от `submit`; оба места; таймауты без запаса — 1000/50 ms по времени прихода строки). Сначала печатаются sha256, PARAMS, build id (сверяется с содержимым) и config id проверяемого артефакта. Каждая игра повторяется с in-process `current` и PARAMS артефакта; строки команд обеих сторон обязаны совпасть (`sameAsCurrent` по всем играм), кроме метки: на ходу 0 артефакт обязан напечатать ровно свою метку там, где у `current` пустой TRAIN. Игра, где соперник снят (таймаут или неверный вывод) хотя бы в одном из двух прогонов, не сравнивается и проваливает проверку (`notCompared`; `minTurns` показывает самую короткую игру). Провал также при лишних строках stdout и любых строках stderr, кроме `SLOW turn`; строки, пришедшие после пропущенного дедлайна, считаются отдельно (`lateLines`). Код выхода 1 при любом провале. При таймауте печатается команда повтора для seed с теми же `-Pparams`. После пропущенного дедлайна артефакт получает 2 s, чтобы дописать ответ и SLOW-отчёт; не успевший убивается, и заметка говорит «no conclusion». Провал только из-за таймаута, когда артефакт доработал до конца без SLOW-отчёта (задержка вне его собственного хода; на ходу 0 его часы стартуют с первого токена ввода, после запуска JVM и init), перечитывается после тихого повтора названных seed, записываются оба результата. Процессы запускаются без JDK_JAVA_OPTIONS, JAVA_TOOL_OPTIONS и _JAVA_OPTIONS (в любом регистре). Проверка показывает, что упаковка не меняет игру исходного бота на достигнутых позициях; логику бота она не проверяет |

Победы — по рангам CG (они упорядочивают и игры с равным счётом, их считает `scoreTies`) |

Каждая игра сначала сверяется с симулятором (как в cgValidate), затем на ходах с подтверждённым состоянием две строки бота сравниваются с записанным stdout агента, а игра идёт дальше по записанным командам обоих игроков. Java-файл (`submit` = `build/submit/Player.java`, `file:<путь>`) компилируется из тех байтов, чей sha256 печатается вместе с PARAMS. Вердикт игры: SAME (сравнены все записанные ходы, расхождений нет), DIFF (расхождение или бот не ответил там, где агент ответил), PARTIAL (расхождений нет, но сравнены не все ходы), ERROR; код выхода 0, только если все игры SAME. Печатаются build id и config id Java-файла и записанная метка каждой игры — даже если ход 0 не сравнивался (`marker`, сводка `markers`). Бот, печатающий метку, обязан повторить записанную, а боту с пустым TRAIN на ходу 0 (in-process или сборка до метки) записанная метка прощается, поэтому SAME подтверждает игру, а сборку называют метки. Для проверки загрузки — копия загруженного артефакта `-Pbot=file:replays/artifacts/<первые 8 hex sha256>/Player.java` (вне Git; `build/submit` меняется с каждой сборкой). Совпадение показывает поведение на достигнутых позициях, а не аттестацию кода |

## Сравнение версий

Политика P2 от 2026-10-30, подробно — `docs/local-screen.md`.

- Базовая версия (контроль): версия, которую заменяет кандидат, то есть локальный чемпион — последняя версия, прошедшая P2. Сейчас это v01: `cr.bot.v01.GreedyBot` со снимком `src/main/resources/cr/bot/versions/v01.properties`, она же выбранная версия P1. Кандидат — `current` со своим флагом, остальные флаги выключены.
- Набор соперников (P2, проверка PV1 от 2026-10-30):
  - прямой матч с контролем;
  - `boss` — Default AI из referee-репозитория (один барак рыцарей, без уклонения; v01 выигрывает у него 95 %); это только нижняя планка, не модель Princess Boss;
  - `old` — код записи 3315948 (19.64), запуск внешним процессом из `refs/old-3315948/Player.java` (вне Git, файл кладёт пользователь; пока его нет).
  Внешние процессы запускаются с `-Pthreads=3 -PturnMs=200`, серии внутри процесса — с `-Pthreads=8 -PturnMs=50`.
- Seed для разработки: все seed < 200000 (включая уже использованные) и фикстуры.
- Отдельный набор для итоговой оценки:
  - скрин — свежий блок `200000 + 2000·k` из 2000 карт на кандидата (внешние соперники играют первые 500 карт блока);
  - итоговая оценка перед загрузкой — блок `400000 + 2000·k`, один раз;
  - реестр блоков — `docs/data/seed-ledger.json`.
- Перестановки сторон / мест и политика случайности: каждая карта (`MapGen`, `java.util.Random(seed)`) играется дважды с обменом мест свежими ботами. SEED ботов = 1, все боты детерминированы, поэтому повторный прогон тех же seed новых данных не даёт.
- Основная метрика и критерий принятия изменения:
  - метрика — S, счёт по картам (2 игры, ничья = ½), 95 % CI по картам (`± 1.96·SD/√карт`);
  - против общих соперников — Δ = S(кандидат) − S(контроль), парно по картам;
  - G0 — у кандидата 0 сбоев;
  - G1 — прямой матч, нижняя граница CI для S > 0.50;
  - G2 — Δ против `boss` ≥ −2 pp;
  - G3 — Δ против `old` ≥ −2 pp, пока `old` нет — пропуск записывается;
  - точечный фикс (меняет < 10 % карт): G0, S ≥ 0.500, Δ против `boss` ≥ −1 pp и регрессионный тест;

- Правила учёта ничьих, ошибок, нелегальных ходов и таймаутов:
  - ничья = ½, число ничьих отчитывается;
  - любой сбой кандидата (ошибка, таймаут, медленный ход, лишняя строка) проваливает G0;
