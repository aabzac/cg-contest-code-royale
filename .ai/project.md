## Пути и команды

Укажите точные команды вместе с аргументами и требуемыми зависимостями.
Разделяйте проверку корректности, запуск матчей и измерение времени.

| Назначение | Путь или команда |
| --- | --- |
| Исходники бота | `src/main/java/cr/bot/` (`current/` — разрабатываемый, `vNN/` — замороженные), раннер `cr/submit/CGRunner.java` |

Спека бота: `name` или `name?K=v,K2=v` (параметры есть только у `current` и `v01`; у `submit`, `boss`, `v00` это ошибка, параметры артефакта задаёт `submit -Pparams`). У процесс-ботов (`submit`, `boss`, `proc:`) лишняя строка вывода, как на CG, читается как следующий ответ; run и bench показывают `extraLines` |
| Сверка симулятора с referee | `./gradlew cgValidate -Preplays=replays/cg` и `-Preplays=replays/cg2` (строгий режим; ожидается: все ходы совпадают, расхождение только `winner 0 vs -1` в играх 911493205 и 908057307). Опции: `-Pverbose=1`, `-Presync=true`, `-PlogResync=true`, `-Pquiet=true`, `-PdumpState=true`, `-Pconsts=NAME=v,ARR[i]=v` |
| Профилирование и измерение времени ходов | Не задано |
| Подготовка файла для отправки на платформу | `./gradlew submit [-Pparams=K=v,...]` → `build/submit/Player.java`: только ASCII и LF при любом checkout и ОС (CRLF → LF, одиночный CR — ошибка; файлы каталога по имени), поэтому sha256 определяется кодом. Параметры проверяются через `Params.apply` и на допустимость в строковом литерале, печатаются действующие; лимит 100 000 символов. Больше одного аргумента — ошибка (на Windows кавычка в `-Pparams` разрывает аргумент). Все проверки, включая имена файлов и единственность маркера PARAMS, идут до записи. Новый артефакт собирается в `build/submit.new` и заменяет `build/submit` только после компиляции, так что любой сбой оставляет старый артефакт целиком; сбой виден по коду выхода 1 (procCheck тогда не запускается) |
| Проверка точного артефакта отдельным процессом | Перед каждой вставкой: `./gradlew procCheck -Popp=v01 -Pgames=100 -PseedBase=5000` и `-Popp=boss -Pgames=100 -PseedBase=6000` (зависит от `submit`; оба места; таймауты без запаса — 1000/50 ms по времени прихода строки). Сначала печатаются sha256 и PARAMS проверяемого артефакта. Каждая игра повторяется с in-process `current` и PARAMS артефакта; строки команд обеих сторон обязаны совпасть (`sameAsCurrent` по всем играм). Игра, где соперник снят (таймаут или неверный вывод) хотя бы в одном из двух прогонов, не сравнивается и проваливает проверку (`notCompared`; `minTurns` показывает самую короткую игру). Провал также при лишних строках stdout и любых строках stderr, кроме `SLOW turn`; строки, пришедшие после пропущенного дедлайна, считаются отдельно (`lateLines`). Код выхода 1 при любом провале. При таймауте печатается команда повтора для seed с теми же `-Pparams`. После пропущенного дедлайна артефакт получает 2 s, чтобы дописать ответ и SLOW-отчёт; не успевший убивается, и заметка говорит «no conclusion». Провал только из-за таймаута, когда артефакт доработал до конца без SLOW-отчёта (задержка вне его собственного хода; на ходу 0 его часы стартуют с первого токена ввода, после запуска JVM и init), перечитывается после тихого повтора названных seed, записываются оба результата. Процессы запускаются без JDK_JAVA_OPTIONS, JAVA_TOOL_OPTIONS и _JAVA_OPTIONS (в любом регистре). Проверка показывает, что упаковка не меняет игру исходного бота на достигнутых позициях; логику бота она не проверяет |
| Сохранение текущей arena entry перед новой загрузкой | `python -I tools/arena_snapshot.py <agentId> aabzac <league> docs/data/arena-<agentId>-<событие>-<дата>.json replays/cg/arena-<agentId>/<событие>-raw` (строка лидерборда без личных полей и последние бои; сырые ответы вне Git). Строка ищется по нику (фильтр KEYWORD, без ограничения в 1000 строк), новый agentId берётся из неё, другая лига печатается (повышение). Код старой записи пользователь сохраняет из IDE до вставки нового |
| Скачивание игр агента | `python -I tools/arena_games.py <agentId> replays/cg/arena-<agentId>/games docs/data/arena-<agentId>-games-<дата>.json [сохранённые списки боёв...]`: сырые ответы `gameResult/findByGameId` без изменений (вне Git) и манифест (место агента, соперник, ранги, счёт, seed, sha256). Живой список боёв сохраняется рядом с играми (`battles-<время>.json`) и объединяется с переданными сохранёнными списками (например, из снимков `arena_snapshot.py`), поэтому игры агента остаются в манифесте после его замены. Игра считается законченной, если так говорит любая строка или её файл уже сохранён; повторный запуск докачивает только новые; неполный ответ — failure, не сохраняется и не останавливает запуск. Победы — по рангам CG (они упорядочивают и игры с равным счётом, их считает `scoreTies`) |
| Проверка кода, сыгравшего на арене | `./gradlew cgAttribute -Preplays=replays/cg/arena-<agentId>/games -Pagent=<agentId> [-Pbot=submit\|file:<Player.java>\|<спека>]` (replays и agent обязательны; pseudo, совпавший у нескольких agentId, — ошибка). Каждая игра сначала сверяется с симулятором (как в cgValidate), затем на ходах с подтверждённым состоянием две строки бота сравниваются с записанным stdout агента, а игра идёт дальше по записанным командам обоих игроков. Java-файл (`submit` = `build/submit/Player.java`, `file:<путь>`) компилируется из тех байтов, чей sha256 печатается вместе с PARAMS. Вердикт игры: SAME (сравнены все записанные ходы, расхождений нет), DIFF (расхождение или бот не ответил там, где агент ответил), PARTIAL (расхождений нет, но сравнены не все ходы), ERROR; код выхода 0, только если все игры SAME. Совпадение показывает поведение на достигнутых позициях, а не аттестацию кода |
| Журнал экспериментов и сырые результаты | `docs/DEVLOG.md`, `docs/BOTS.md`, `docs/STATUS.md`, `docs/PLAN.md`; отчёты бенча `build/bench/`; корпуса реплеев — `replays/` (gitignored), манифесты с sha256 — `docs/data/` |

## Особые правила проекта

- Старый проект `C:\Disk_D\Programming\IdeaProjects\CodeRoyale\` — только справка; код из него не переносить.
- `refs/referee-csj/` — референс для порта правил и генератора карт (`java.util.Random(seed)`, seed есть в `refereeInput` реплея); при порте использовать live-константы (250 ходов), а не значения репозитория.
- Правила живут только в `core`; каждое изменение правил — тест и зелёная сверка с реплеями.
